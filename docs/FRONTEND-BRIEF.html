Frontend NoteNest

Buku catatan pribadi yang halamannya bisa dipinjamkan untuk dibaca. Dokumen ini menjelaskan apa yang dibangun, sampai batas mana, bagaimana dummy data ditukar dengan API asli, dan seperti apa wujudnya.

Bagian 1

PRD

Apa yang dibangun, untuk siapa, dan sampai batas mana.

1.1Tujuan

NoteNest hari ini adalah API tanpa wajah. Frontend ini mengubahnya jadi produk yang bisa dipahami dalam dua menit oleh orang yang tidak akan pernah membaca kode Java-nya.

Tujuan utama

Satu alur utuh: tulis catatan → cari & filter → bagikan ke teman → teman membacanya → cabut akses.

Tujuan kedua

Menunjukkan frontend paham batas backend: identitas dari token, owned menentukan aksi, 401 dan 403 diperlakukan berbeda.

Bukan tujuan

Bukan Notion. Tanpa rich text, tanpa edit bersama, tanpa realtime, tanpa folder.

1.2Keputusan: folder frontend/ di repo yang sama

ShopNest memilih repo terpisah. NoteNest tidak, karena alasan yang berbeda:

  • Proyek ini ada supaya frontend-nya selesai. Satu repo membuat portfolio utuh bisa dibaca dari satu tautan.
  • Kontrak API kecil dan bisa berubah bersama UI. Perubahan DTO dan tipe TypeScript-nya masuk di commit yang sama, jadi tidak bisa melenceng diam-diam.
  • Toolchain tetap terpisah secara fisik. Semua modul Maven ada di backend/; Node hanya hidup di frontend/. .gitignore root sudah mengenal node_modules/ dan dist/.

1.3Framework: React + TypeScript + Vite

Pertanyaan sebenarnya adalah "perlu server rendering atau tidak". Gateway mengautentikasi lewat header Authorization: Bearer, bukan cookie — server Next.js tidak bisa membaca token di browser tanpa memindahkannya ke cookie, yang berarti mengubah gateway. Semua halaman NoteNest juga butuh login, jadi SEO tidak relevan.

1.6Kontrak API yang harus ditiru

Data dummy harus berbentuk persis seperti data asli, sampai ke nama field dan bungkusnya. Semua di bawah disalin dari DTO backend.

Amplop response — seragam, termasuk error dari gateway

type ApiResponse<T> = {
  success: boolean
  message: string          // "Notes found", "Invalid or expired token", …
  data: T | null           // null saat error, kecuali validasi (lihat bawah)
}

type PageResponse<T> = {  // hanya GET /api/notes
  content: T[]; page: number; size: number
  totalElements: number; totalPages: number; last: boolean
}

Tipe domain

type AuthResponse = {
  accessToken: string; tokenType: "Bearer"
  userId: string; email: string; displayName: string
  role: "USER" | "ADMIN"      // selalu USER dari register; tidak dipakai UI
}

type Note = {
  id: string; ownerId: string
  title: string
  content: string | null
  tags: string[]              // lowercase, sudah di-trim, tanpa duplikat
  owned: boolean              // SATU-SATUNYA penentu tombol aksi
  ownerEmail: string | null        // terisi hanya di shared-with-me
  ownerDisplayName: string | null  // terisi hanya di shared-with-me
  createdAt: string; updatedAt: string   // "2026-09-17T10:14:03.221" — TANPA zona
}

type Share = {
  id: string; noteId: string
  sharedWithUserId: string    // dipakai untuk DELETE /{id}/share/{userId}
  sharedWithEmail: string
  permission: "READ"
  createdAt: string
}

type UserSummary = { userId: string; email: string; displayName: string }

type Profile = {
  id: string; userId: string; email: string; displayName: string
  bio: string | null; avatarUrl: string | null
  createdAt: string; updatedAt: string
}

1.7Strategi dummy data

Prinsipnya satu: komponen tidak boleh tahu bahwa datanya palsu. Satu if (isMock) di dalam komponen berarti pekerjaan ulang saat penyambungan.

// src/mocks/handlers.ts — cegat di lapisan jaringan
http.get("*/api/notes", ({ request }) => {
  const me = userFromAuthHeader(request)          // tiru gateway: 401 kalau tidak ada
  if (!me) return HttpResponse.json(
    { success: false, message: "Missing or invalid Authorization header", data: null },
    { status: 401 })
  const url = new URL(request.url)
  // filter owner → tag → q, lalu sort + potong halaman
  return HttpResponse.json({ success: true, message: "Notes found", data: page })
})

Isi data dummy yang layak

  • Tiga akun — Ani, Budi, Citra — supaya share bisa diuji dari dua sisi. Sediakan cara cepat berganti akun di mode dev.
  • 25–30 catatan milik Ani — cukup untuk tiga halaman dengan size=10.
  • Judul 200 karakter persis; isi kosong (null); isi 20.000 karakter; isi dengan banyak baris baru.
  • Catatan tanpa tag, dengan 1 tag, dan dengan 10 tag.
  • Budi menerima 4 catatan dari Ani dan Citra — cukup untuk menguji label pemilik berbeda.
  • Citra tidak ada di hasil cari sampai "login pertama" — tiru aturan profil lazy.
  • Handler yang bisa dipaksa gagal (?__fail=502) untuk menguji keadaan error.

Penukaran ke API asli

  1. Isi VITE_API_BASE_URL=http://localhost:8080.
  2. Matikan pendaftaran worker MSW di main.tsx.
  3. Pastikan origin dev ada di CORS_ALLOWED_ORIGINS gateway.
  4. Ulangi alur penuh dengan dua akun; selisih bentuk response berarti §1.6 yang salah, bukan komponennya.

Handler MSW tidak dibuang — pindahkan ke test komponen.

1.8Celah backend yang mempengaruhi frontend

Ditemukan saat membaca kode. Tidak satu pun menghalangi fase dummy, tapi semuanya muncul di hari penyambungan. Urut dari yang paling pasti menggigit.

1Urutan default catatan terbalik

@PageableDefault(size = 10, sort = "updatedAt") tanpa arah = naik. Tanpa parameter, catatan paling lama muncul paling atas. Selalu kirim sort=updatedAt,desc. MSW harus meniru default yang salah ini juga, supaya lupa mengirim parameter ketahuan sejak fase dummy.

2Pengguna tidak bisa ditemukan sebelum profilnya ada

Register tidak membuat profil; GET /api/users/me yang membuatnya. Pencarian user dan share membaca tabel profil. Akibatnya: teman yang baru mendaftar tapi belum pernah memicu /me tidak bisa dibagikan catatan — share membalas 404. Frontend menutup sebagian besar kasus dengan memanggil /me tepat setelah login/register (§1.5).

3shared-with-me gagal total kalau satu pemilik hilang

Untuk tiap catatan, note-service menanyakan pemiliknya ke user-service. Kalau satu pemilik tidak punya profil, seluruh daftar dibalas 404 — bukan satu item yang kosong. Jarang terjadi setelah poin 2 ditangani, tapi tampilkan sebagai error umum dengan coba lagi, bukan "tidak ditemukan".

4Tidak ada endpoint daftar tag

Filter tag dibangun dari tag di halaman yang sedang dimuat, digabung dengan tag yang pernah diketik pengguna. Jangan janjikan "semua tag".

5shared-with-me tanpa pagination, pencarian, atau filter

Semua dikirim sekaligus, urut dari yang terakhir dibagikan. Kalau perlu cari, lakukan di klien atas data yang sudah dimuat — dan beri label jelas bahwa itu hanya menyaring daftar di layar.

6Nama di token bisa basi

displayName di AuthResponse berasal dari tabel auth dan tidak ikut berubah saat profil diubah. Setelah PUT /api/users/me, perbarui nama di state klien dari response profil, bukan dari token.

7Tidak ada refresh token

Token berlaku 24 jam (jwt.expiration=86400000). Setelah itu 401 — rancang sebagai "sesi habis, masuk lagi". Simpan draf catatan yang sedang ditulis di localStorage supaya tidak hilang saat sesi habis di tengah menulis.

8Perubahan tidak realtime

Penerima baru melihat perubahan atau pencabutan akses setelah memuat ulang. Aktifkan refetchOnWindowFocus untuk query catatan pinjaman; kalau detail tiba-tiba 403, akses sudah dicabut — tampilkan pesan itu dengan jelas.

1.9Definition of done & urutan kerja

Selesai berarti
  • Setiap halaman punya empat wajah: memuat, kosong, gagal, terisi
  • Semua tanggal lewat satu fungsi format
  • Form menolak input yang pasti ditolak backend
  • 401 mengakhiri sesi dengan bersih; 403 tidak
  • Tidak ada tombol aksi pada catatan dengan owned: false
  • Terbaca di 375px, editor termasuk
  • Kontras ≥ 4.5 : 1, termasuk teks di atas kartu pastel; keyboard bisa menjangkau semua aksi

Bagian 2

Design system

Tema pastel, terang saja. Warna diambil dari prototipe Lovable, font dari ian-portfolio. Halaman ini memakai token yang didefinisikannya — yang terlihat di bawah adalah hasil nyatanya.

2.1Tiga prinsip

Warna milik catatan

Latar dan UI tetap tenang: biru keabuan muda, putih, navy. Warna pastel hanya dipakai kartu catatan, supaya warnanya berarti "ini isimu".

Teks gelap di atas pastel

Abu-abu biasa gagal kontras di semua pastel (2.4–3.2 : 1). Di atas kartu, teks selalu navy --foreground atau --on-pastel.

Pinjaman ditandai bentuk

Kelima pastel sudah dipakai kartu, jadi catatan pinjaman tidak bisa ditandai warna. Penandanya garis putus-putus dan chip "dibagikan oleh…".

2.2Tipografi — Geist

Satu keluarga untuk semuanya, sama dengan ian-portfolio. Hierarki dibangun dari ukuran dan berat, bukan dari font kedua. Hanya berat 400, 500, dan 600 yang dimuat — jangan pakai font-bold (700), browser akan memalsukannya.

Warna kartu ditentukan dari id, bukan disimpan

Backend tidak punya kolom warna. Supaya satu catatan selalu tampil dengan warna yang sama — di daftar, detail, dan di layar penerima share — warnanya diturunkan dari id:

const NOTE_COLORS = ["blue", "pink", "yellow", "mint", "lilac"] as const

export function noteColor(id: string) {
  let h = 0
  for (const ch of id) h = (h * 31 + ch.charCodeAt(0)) >>> 0
  return NOTE_COLORS[h % NOTE_COLORS.length]   // → class "bg-note-" + warna
}

Jangan menurunkan warna dari tag atau judul: keduanya bisa diubah, dan kartu yang tiba-tiba berganti warna setelah disunting terasa seperti bug.

2.6Responsif & aksesibilitas

  • ≥ 960px: header dengan navigasi (Catatan saya, Dibagikan ke saya, Profil), grid kartu 3 kolom, panel bagikan di kanan detail.
  • < 640px: daftar satu kolom, panel bagikan layar penuh, tombol simpan editor menempel di bawah.
  • Tema terang saja. Jangan pasang prefers-color-scheme: dark sampai tema gelap didesain.
  • Kontras ≥ 4.5 : 1 — ikuti tabel §2.3. Garis putus-putus dan chip teks adalah penanda pinjaman, bukan warna.
  • Fokus selalu terlihat (--ring). Dialog hapus menjebak fokus dan mengembalikannya ke pemicu.
  • Hormati prefers-reduced-motion: matikan angkat-kartu dan animasi kerangka.
